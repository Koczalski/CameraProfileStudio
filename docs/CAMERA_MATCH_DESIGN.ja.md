# カメラマッチ 再設計（調査と計画）

状態: 案。実装には着手していない。2026-11-07 時点。

## 1. 結論

カメラマッチに求められている中心の仕事は、同じ場面を2通りに写した画像の組から、片方の見え方をもう片方に合わせる3D LUT を作ることです。最も需要がありそうな使い方は、RAW 現像の結果を、カメラ内 JPEG の絵作りに合わせることです。2台のカメラの色合わせと、カラーチャートによる校正は、その次に来ます。

今の実装は、エンジンの部品（CCM、トーンカーブ、残差3D格子、ホールドアウトの ΔE00、パッチ別の誤差、焼く誤差）がそろっています。足りないのは入口です。画像1組ずつしか扱えず、色の網羅が不足し、同じカメラの RAW と JPEG でも位置合わせで止まりやすく、チャートは CSV を自分で作る必要があります。直すのはエンジンではなく、データの集め方、サンプリング、位置合わせ、検証の単位です。

要求仕様 S3-09 は、入力に「RAW/JPEG ペア、2台のカメラ、色票、参照画像」を挙げています。参照画像（無関係な写真）は、画像ルック作成が受け持つと決めたので、ここでは扱いません。

## 2. 調査

同種のツールと議論を調べました。確認できたのは検索結果と一部のページの要約です。PyPI のページは取得に失敗し、検索結果に載った README の要約で代えています。

- RAW+JPEG のペアから LUT を作る `darktable-lut-generator` は、フォルダー内の RAW と JPEG の組を読み、単位 LUT との差を正則化つきの線形回帰で推定します。色の網羅を重視し、色の密度の逆数で重みを付けて標本を取ります。付属のテストパターンを画面に出し、露出を変えて5組ほど撮る使い方を勧めています。色域の端にはアーティファクトが残ると書かれています。
- pixls.us の議論（OOC スタイルの3D LUT）では、格子は 9³ や 16³ で足り、大きくすると汎化が悪くなる、という報告がありました。標本の数より色の網羅が効く、とも書かれています。自動の位置合わせが収束しない例、色域外やハイライトの飽和でペアの対応が崩れる例も出ています。LUT は表示参照なので、強いトーンカーブを持つ絵作りは現像側のカーブの代わりになり、重ねがけはできません。
- DaVinci Resolve の Color Match はチャートを使います。チャートの位置合わせは手作業で、自動認識は信用されていない、という実務者の声があります。Mixing Light の記事は、色相の向きを合わせることが彩度より大事で、まず同じカメラ同士で試してから使うよう勧めています。
- Resolve の Shot Match や Colourlab Ai は、基準となるカットに他を寄せる統計的な方法です。無関係な参照写真に寄せる方式なので、本機では画像ルック作成にあたります。
- DCamProf のような profiling の道具は、カメラ内 JPEG を直接プロファイルにするのは難しいとされ、RAW を基にして、ルックはトーンカーブなどで足す考え方です。

## 3. 現状とのずれ

コードを読んで確かめた事実と、推測を分けて書きます。

| 番号 | ずれ | 根拠 |
|---|---|---|
| G1 | 画像1組しか扱えない | `MatchWorkspace` は元画像と目標画像を1枚ずつ持つ。エンジンは `SamplePairs` に group を持ち、複数の標本集合を結合できるが、画面からは使えない |
| G2 | 標本が画素の一様ランダム | `sample_image_pair` は画素を一様に最大20000点取る。画像に多い色が標本の大半になり、飽和色や暗部、明部が薄くなる |
| G3 | 同じカメラの RAW+JPEG でも位置合わせに頼る | `sample_image_pair` は画像の形が同じことを要求する。先日のログでは JPEG が 2048×1361、RAW 現像が 2048×1365 だった。同機のペアでも画素数がずれる可能性が高く、その場合は ORB の位置合わせに入る。実際のペアでの確認は〔要確認〕 |
| G4 | ホールドアウトが同じ画像の中 | 空間ブロック(8×8)で分けるため、別の場面への汎化は測れない。複数ペアなら、ペア単位で取り分けられる |
| G5 | 色の網羅が見えない | どの色相や明るさの標本が足りないかを、利用者に示す仕組みがない |
| G6 | チャートの入力が重い | CSV の列を自分で用意する。基準値の内蔵も、画像上のパッチ読み取りもない |
| G7 | 導線が弱い | 必要なデータ、同じ番号の RAW と JPEG を選ぶこと、撮り方の案内が画面にない |

## 4. 方針

- 主役は「RAW+JPEG の複数ペアから絵作りの LUT を作る」にする。2台のカメラの合わせとチャートは同じ部品の別の入口とする。
- 無関係な参照写真は引き続き扱わない。画像ルック作成に案内する（実装済み）。
- 局所処理（ノイズ除去、シャープネス、レンズ補正、場所によって変わる補正）は再現しない。これは LUT の限界として画面にも書く。
- 精度は検証用のデータで測った ΔE00 で示す。実機で確かめるまでは、今と同じく「未検証」の表示を残す。
- 依存を足さない。固定済みの OpenCV、SciPy、Pillow の範囲で作る。

## 5. 計画

### フェーズ1: RAW+JPEG の複数ペア（最優先）

1. ペアの集め方
   - フォルダーを指定すると、拡張子を除いた名前が同じ RAW と JPEG を自動で組にする（例: `IMGP9694.PEF` と `IMGP9694.JPG`）。
   - 一覧に組ごとの状態（読み込み済み、位置合わせの結果、採用/除外）を出す。組は後から足したり外したりできる。
   - 名前が合わない画像は手動で組にできる。今の1組ずつの入力は、その特別な場合として残す。
2. 同じカメラの位置合わせ
   - 画像の形の差が小さいときは、中央を合わせ、微小な平行移動と拡大を相関で補正する。結果を残差で検証し、通らなければ ORB に切り替える。
   - 失敗したときは、特徴点の数や形の差など、原因を画面に出す。
3. 標本の取り方
   - 目標の色の密度で重みを付け、色空間に均等に近い標本を取る。外れ値と、クリップした画素は除く。
   - 各ペアから逐次に標本だけを取り出し、画像全体は保持しない（メモリを抑える）。
4. 検証
   - ペア単位でホールドアウトを取り、別の場面への汎化を ΔE00 で出す。既存のパッチ別レポートと焼く誤差は、そのまま使う。
   - 色相ごとの標本数と誤差を表示し、足りない色を知らせる。
5. 既定値
   - 残差格子の既定を 9 にする（調査の知見は、小さい格子ほど汎化しやすい）。
6. 撮り方の案内
   - 画面に短く書く: 色の多い被写体、露出を変えた3〜5組、レンズ補正はカメラ側で切る、JPEG は sRGB で撮る。

### フェーズ2: 2台のカメラとチャート

1. 2台のカメラは、今の ORB 経路を維持し、失敗理由ごとの対処を出す。複数ペアはフェーズ1の仕組みを使う。
2. チャートは、ColorChecker Classic の24色の基準値を内蔵し、画像上で四隅を指定するとパッチの平均を自動で読む。CSV の入力は残す。基準値の出典と権利は〔要確認〕。

### フェーズ3: 検証と出力

STATE.md の残りの候補を入れる。独立した検証コマンド、正則化の掃引、露出変化への耐性テスト、CLF など他形式の書き出し。

## 6. 非目標

- 局所処理の再現（ノイズ除去、シャープネス、DRO、周辺減光、レンズ補正）
- 無関係な参照写真からの推定（画像ルック作成の領域）
- RAW のカメラリニア空間での処理、HDR
- 実機 JPEG との一致の保証

## 7. リスクと未確認

- 実機での検証がない。今ある検証データは合成のものだけで、ペンタックス K-7 などの実ペアでの確認が要る。利用者の協力が必要。
- Adobe RGB で撮った JPEG は、ICC がないと sRGB として読まれ、色がずれる。色空間を手動で選べるようにするか、警告を強める。ペンタックスでは、先頭が `_` のファイル名が Adobe RGB の撮影にあたる。
- 絵作りに、場面によって変わる処理（自動コントラストなど）が入っていると、全体で1つの LUT には収まらない。誤差が大きい色や明るさを検証の表で示す。
- ペア数が増えると処理時間が延びる。ジョブとキャンセルの既存の作法に従い、逐次処理にする。

## 8. 決めたこと

2026-11-07 に、次のとおり決めた。利用者の確認が要るのは4だけ。

1. 版: フェーズ1は 0.2.9-beta に入れる。0.2.8-beta は版上げが済み、ビルド前の状態なので、機能を足さずに出す。
2. 入口: 新しい手順の画面は作らず、今のカメラマッチの画面を拡張する。「画像ペア」のモードを、組の一覧（追加、除外、状態の表示）に置き換える。1組だけの使い方は、一覧に1件だけある場合として残る。ナビの項目と画面の数は変わらないので、ショートカットや既存のテストが指す位置も動かない。
3. 色空間の手動指定: フェーズ1に含める。未タグの画像に限り、sRGB と Adobe RGB を選べる。新しい依存は要らない。`lcms.py` に、原色から RGB プロファイルを作る `cmsCreateRGBProfileTHR` がすでにあり、Adobe RGB (1998) は原色と D65、ガンマ 2.2 で作れる。ICC が埋め込まれている画像には効かせない。
4. 実ペアでの検証: 利用者の RAW+JPEG を使う。リポジトリには入れず、パスを指定して手元で測る。利用者が3〜5組の同番号ペア（同じ機種、露出を変えたもの、色の多い被写体）を用意する必要があり、これは実装の前に利用者の作業として残る。
